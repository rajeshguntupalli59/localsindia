## 1. What This Is

LocalsIndia (localsindia.com) — free local directory + classifieds for South India. ~35,300 real businesses (from OpenStreetMap) + real-user listings, by city → category → neighbourhood; WhatsApp-native contact, free to post and to claim. 150 cities in 6 states (AP 36, TN 33, Karnataka 32, Telangana 28, Kerala 20, Puducherry 1). Live in production on Azure. **Plain-English overview of how everything works: README.md.**

- Web: https://www.localsindia.com (Next.js 14, Azure Static Web Apps, hybrid SSR)
- Backend: https://localsindia-backend-in.azurewebsites.net (FastAPI, Azure App Service)
- Mobile: React Native + Expo 56, EAS builds. **Live in production on Google Play since 2026-08-11.** Builds: versionCode 12 (2026-08-10, first production release), 13 (2026-08-14), 14 (2026-08-31, mobile reCAPTCHA, commit 9ac90a2 — uploaded by Raj; confirm its rollout in Play Console). All versionName 1.0.0. Since v14 the only app changes are commit 3630dc4 (business directory, claim, hours) + 5380e26 (removed dead `claim()`).
- GitHub: https://github.com/rajeshguntupalli59/localsindia

### 4a. AI image/video pipeline (manual, not scheduled)

`agents/assets/ai_generated/` (raw) and `ai_generated_branded/` (logo + `localsindia.com` + "Download Free App" CTA composited top/bottom via ffmpeg) — 23 images as of 2026-08-14, generated via ComfyUI (Stable Diffusion 1.5) running on a **free Google Colab T4 GPU**, driven directly through ComfyUI's REST API from chat (not a script in this repo). 5 promo videos (ffmpeg: real Play Store screenshots + these AI images + Pixabay royalty-free music, crossfade transitions) were delivered to the founder but not committed (large binaries).

**Why this isn't scheduled**: Colab requires a manual browser session (~90min idle / ~12hr max timeout, new tunnel URL every session) — the GitHub Actions cron workflows can't reach it. Generating more images/videos is an on-request "hey Claude, generate N more" action, not automated.

**Publishing is manual, on-request only** — founder's explicit call each time ("whenever I think is ok I will ask you to publish"), not a standing schedule. `agents/meta_client.py` gained real video support 2026-08-14 (`upload_video_to_cloudinary`, `post_to_facebook_video`, `post_to_instagram_reel` — Reels need a status-poll loop before `media_publish` will succeed, unlike images) since it previously only handled photos. First real posts 2026-08-14: 1 video (FB + IG Reel) + 2 branded images (FB + IG feed) — see `agents/output/video_posts_log.jsonl` (gitignored, local record only).

**AI-*generated* (motion, not slideshow) video — working as of 2026-08-14 evening.** Chose Wan2.2 **5B** over 14B: the 14B variant needs two ~13.3GB diffusion passes (high/low noise) that would consume the T4's entire 16GB VRAM before the text encoder, VAE, or actual video latents even load — real OOM risk, never attempted. 5B is a single ~9.3GB UNET (~16.9GB total download incl. text encoder + VAE) that fits comfortably. Verified with a real image-to-video generation (the city-market photo animated, 49 frames/20 steps/1280x704/24fps) — succeeded, but **took ~11.5 minutes for 2 seconds of output** on the T4. Real capability, not just theoretical, but slow enough that it's a "when it matters" tool, not a casual one. The Z-Image-Turbo + Fun ControlNet Union models (~25.5GB) are separately downloaded and verified for image **inpainting** (unrelated node graph).

**Known bug, fixed downstream (not in ComfyUI itself)**: ComfyUI's `SaveVideo` node writes the `moov` atom at the *end* of the mp4 (no faststart), which breaks inline playback in most web viewers/players until the whole file downloads. Every video pulled from ComfyUI needs `ffmpeg -c copy -movflags +faststart` (lossless remux, no re-encode) before it's actually usable anywhere web-facing.

**Persistence across sessions — investigated, not viable right now.** Every session re-downloads all ~44GB of models from scratch (Colab's `/content` disk is wiped on disconnect/restart) — costs ~15-20 min at the start of every session. The fix would be mounting Google Drive and pointing the models folder there so downloads persist. **Blocked**: the founder's Drive has no free space, and even fully cleared, Google's free 15GB tier can't hold ~44GB of models anyway — would need paid Google One storage (100GB+ tier). Left as a future option, not done. Session was manually disconnected or ended cold on 2026-08-14 rather than pursue this — next Colab session starts from zero again (clone + all model downloads), same as every session so far.

### 2026-08-15 — Security review: fixed JWT type confusion + error-detail leak, untracked backend/.env
- Ran a full-codebase security review (not just a diff review — nothing was pending). Four findings, three fixed immediately since the live backend was at real risk:
- **JWT type confusion (fixed)**: `decode_token()` in `core/security.py` never checked the JWT `type` claim, so any validly-signed token worked as a full access token regardless of what it was actually issued for. Concretely: a **refresh token** (7-day validity, meant only for `POST /auth/refresh`) worked anywhere `get_current_user()` is used — i.e. nearly every protected endpoint — extending a leaked refresh token's blast radius from "can get a new access token" to "has full account access for 7 days." Separately, the `otp_verified` **setup token** (10-min validity, meant only to authorize `POST /auth/password/set`) also worked as a full access token, letting someone who'd only proven OTP possession — not completed login — act as that user for the token's lifetime. Fix: `decode_token(token, expected_type="access")` now rejects tokens whose `type` claim doesn't match; `/auth/refresh` explicitly passes `expected_type="refresh"`. `decode_setup_token` already did this correctly — the bug was that the *general-purpose* decoder didn't.
- **Verbose error disclosure (fixed)**: the global unhandled-exception handler in `main.py` returned raw `f"{type(exc).__name__}: {exc}"` to the client on every unhandled 500 — could leak DB error text, internal paths, or business-logic details. Now logs the full exception server-side (`logger.exception(...)`) and returns a generic `"Internal server error."` to the client.
- **`backend/.env` untracked (fixed)**: was git-tracked despite `.gitignore` listing `.env` — only had placeholder/local-dev values, never a real leak, but any future edit with real secrets would've committed silently (no "new file" warning to catch it). `git rm --cached`. Verified zero production impact first: `backend-azure.yml`'s zip step already excludes `.env` — Azure App Service has never read this file, it uses its own App Settings.
- **`OTP_DEBUG` in production — flagged, not fixed, needs the founder's direct check.** Code default is `False` (safe), but `config.py`'s own comment says *"Set to true on Azure to return OTP in response for testing"* — if that's currently `true` on the live App Service, `POST /auth/otp/send` returns any phone number's real OTP directly in the API response (account takeover without SMS access) and `POST /auth/dev-login` hands out an unauthenticated `role=admin` token. Cannot check Azure's actual runtime env var from a coding session — **founder needs to verify this in Azure Portal → App Service → Configuration directly.**
- Verified safe to ship: all 167 backend tests passed unchanged after the fixes (confirms the refresh flow, auth flow, etc. all still work correctly — the fix only closes the misuse path, doesn't touch legitimate token flows).
